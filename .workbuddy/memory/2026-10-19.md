### 根因（关键更正）

第一轮我判断"部署邮件功能从未存在"—— **错**。用户提供了一封 .eml 实锤，推翻了结论：

```
From: "github-actions[bot]" <noreply@github.com>
Message-ID: <SpeechlessPanda/SpeechlessPanda.github.io/push/refs/heads/main/54d266-69b284@github.com>
Subject: [SpeechlessPanda/SpeechlessPanda.github.io] 69b284: deploy: ...
```

而 **2026-10-15 GitHub 官方下线了该功能**（理由：反垃圾/防滥用，收件人从未同意），

最后收到的是 10-11 那封（对应发布仓 commit 69b284），之后 5 次部署一封没有，时间点吻合。

**教训**：判定"功能不存在"前，先搜仓库外证据（用户邮件、收件箱、官方 changelog）。
`git log -S` 只能证明"本仓库没写过"，不能证明"GitHub 没有这能力"。

## Panda 测试修复 + 两个真实 bug（已发 1.1.7）

### 测试失败的真因：**测试自己的写法，不是被测代码**

`test/post-updated.test.js` 的父测试写成 `t => {...}` 且从未 `await` 子测试。
`t.test()` 返回 Promise，父函数同步返回即被判定完成 → 未排空的子测试全部
标记 `test did not finish before its parent and was cancelled`。
症状极具误导性：**首个子测试通过，其后全部 cancelled**，看起来像代码 bug。

**验证手法**：把所有断言抽出来用 `node -e` 逐条跑一遍，全通过 → 证明模块没问题。
改法：父测试加 `async` + 每个子测试加 `await`。
结果 **49/49 全通过**（原 37 pass / 2 fail / 7 cancelled）。

**其余 4 个测试文件不受影响**：它们用 `describe`/`it`（node:test 内置同步实现）。
**教训**：看到"后面全 cancelled"先怀疑测试异步写法，别急着改被测代码。

### 两个真实 bug（都在 `scripts/panda/lib/post-updated.js`）

**① 引号包裹的假值被当成真实修订** —— `explicitUpdated()` 直接拿原始标量比
`false|null|~`，于是 `updated: "false"` / `'null'` / `"~"` / `""` 都算"有真实修订日期"
→ **向所有订阅者重复推送旧文更新通知**，而文章其实从未修订。
修复：新增 `unquoteYamlScalar()` 先剥一层引号再判断。

**② 冒号前有空格导致重复键** —— YAML 允许 `sticky : true`，但
`ensurePostDefaults` 的存在性检测要求冒号紧贴键名，于是在已有 `sticky : true`
旁边再插一个 `sticky: false`；YAML 重复键后者覆盖前者，**作者写的值被静默丢弃**。
修复：抽出 `HAS_UPDATED_RE` / `HAS_STICKY_RE` 宽松正则。

### 排查过但确认不是 bug 的（省得以后重复查）

- 缩进的 `updated:` 不识别 → **正确**，YAML 顶层键不能缩进
- 多文档 front-matter（正文含 `---`）→ `FM_RE` 只取首个，正确
- `date` 在 `updated` 之后、多个 `date:` → 行为正确
- 正文含 `date:` 行但 front-matter 无 → 正确返回 null
- `sticky: false # 注释` 已存在 → 正确识别，不重复插入
- CRLF 输入下 `ensurePostDefaults` → 正确保持 CRLF
