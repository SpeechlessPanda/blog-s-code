## 关键结论：retry-pages-deploy.yml 的 workflow_run 触发器是死的

发布仓该 workflow 近 50 次运行 **全部是 `schedule`，`workflow_run` 0 次**。

原因：
- `pages build and deployment` 是 GitHub **动态（dynamic）workflow**，不在 `.github/workflows/` 里。
  `workflow_run` 无法监听动态 workflow，按名字过滤永远不命中，且**静默失败**。
- 兜底 cron `*/15 * * * *` 被 GitHub 限流，实际间隔 2.5–6.5 小时（近 8 次实测）。

后果：Pages 部署一旦卡死/失败，站点会**静默停留在旧版本**，而源仓 workflow 显示 success，
人类只能靠肉眼发现。这正是本次问题的放大原因。

- `commit` 对得上且 `status=built` 才通过；`errored` 立刻失败并打印失败运行链接

- `api_get()` 先走 PAT，失败退回匿名 curl（发布仓公开）

**CI 实测通过**：run 41296552929，目标 010e8555，两轮 15s 后 `built`。

本地验证手法（本机无 jq，CI 有）：
造一个只实现 `.xxx // ""` 和 `workflow_runs[0]` 两种 filter 的 jq shim，
再伪造 `gh` 返回固定 JSON，即可把 built / errored / 卡死 / 权限不足 四个分支全跑一遍。

## 已实施：concurrency 串行化（commit `75eea5b`）

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false
```

要点：
- **不能开 `cancel-in-progress: true`** —— 打断 gh-pages 推到一半会留半成品。
- 同组只保留「1 运行中 + 1 排队中」，后来者**顶掉排队者**。
  所以评论风暴 `R1→R2→R3→R4` 收敛成「跑当前 + 补跑 R4」，中间的被 cancelled。
  内容不丢：被顶掉的那些重建也是构建最新 HEAD，R4 覆盖它们。
- push / workflow_dispatch / repository_dispatch 共用同一把锁（ref 相同）。

**实测验证**（run `41296849535` vs `41296869758`）：
push 运行 10:17:45 创建、10:18:47 结束；期间 10:18:01 创建的 dispatch 运行
真正开跑时间是 **10:18:48**（差 1 秒）——排队确实卡在前一个后面。
另有一次 dispatch 在排队态被后来的顶掉，conclusion=cancelled，符合预期。
