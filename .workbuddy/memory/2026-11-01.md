## 友链"部署成功但不显示"排查（已修复）

现象：commit `e02457e`（新增 Clouder0 友链）后 workflow 报 success，线上 `/link/` 没有新条目。

排查路径（可复用）：
1. 源码侧确认改动确实在 commit 里 → `git show e02457e`，只加了 1 条友链。
2. 拉线上页面 vs 发布仓 raw 内容对比：
   - 线上缺 Clouder0，发布仓 `main` 的 `link/index.html` **有** Clouder0
   - → 说明构建 + push 都对，问题在 Pages 发布层
3. `gh api repos/<publish>/pages/builds/latest` → `status: building` 卡死、`pages.status: errored`
4. `gh run view <pages-build-deployment run> --log-failed` → 真因：
   `HttpError: Deployment request failed ... due to in progress deployment.
    Please cancel 73711903... first`（HTTP 400）
   即 Pages 认为上一次部署（`73711903`）仍在进行，拒绝新部署。
5. 线上页面与发布仓 `73711903` 内容 **字节完全一致** → 坐实站点冻结在那次部署。

修复：`gh run rerun 41290876460 --repo <publish> --failed`，一次成功，线上立即生效。
注意 `pages/deployments/{id}/cancel` 端点用 deployments API 的 id 会 404（那是另一套 id），别走这条路。

## 关键结论：retry-pages-deploy.yml 的 workflow_run 触发器是死的

发布仓该 workflow 近 50 次运行 **全部是 `schedule`，`workflow_run` 0 次**。

原因：
- `pages build and deployment` 是 GitHub **动态（dynamic）workflow**，不在 `.github/workflows/` 里。
  `workflow_run` 无法监听动态 workflow，按名字过滤永远不命中，且**静默失败**。
- 兜底 cron `*/15 * * * *` 被 GitHub 限流，实际间隔 2.5–6.5 小时（近 8 次实测）。

后果：Pages 部署一旦卡死/失败，站点会**静默停留在旧版本**，而源仓 workflow 显示 success，
人类只能靠肉眼发现。这正是本次问题的放大原因。

待办（尚未实施，需用户确认）：在 `deploy-from-source.yml` 末尾加「部署后校验」——
push 完轮询发布仓 `pages/builds/latest`，status=errored 就让源仓 workflow 失败并输出原因，
把静默错误变成响亮失败。
